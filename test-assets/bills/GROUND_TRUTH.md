# Bill fixture ground truth

Expected extraction values for the fixtures in this directory. `validate_real.py`
reads the JSON block below and scores live extraction against it, so this file is
the single source of truth for the accuracy gate — not a description of it.

## Synthetic fixtures

Generated by `backend/scripts/make_synthetic_bills.py`. The values are known by
construction: the generator draws these exact numbers onto the image, so a
mismatch is an extraction error, never a disputed reading.

| file | units_consumed | total_amount | billing_days | tariff_slab | period_end | condition |
|---|---|---|---|---|---|---|
| `synthetic_clean.png` | 735 | 5420.00 | 61 | LT-1A | 30/06/2026 | clean render, upright |
| `synthetic_blurred.png` | 284 | 1235.50 | 30 | LT-1B | 15/05/2026 | gaussian blur 0.8, -12% brightness, rotated 1.5° |
| `synthetic_highusage.png` | 1450 | 12180.00 | 62 | LT-1C | 12/07/2026 | high consumption, rotated -0.8° |

No fixture may reuse the MOCK_MODE canned values (620 units / Rs 4800) — a
fixture that matched them would let a mocked run score as a partial pass, which
is exactly the silent failure the accuracy gate exists to prevent.

**These are a floor, not a pass.** Generated noise is not real noise: a phone
photo of an actual TNEB bill has perspective skew, uneven lighting, glare, print
wear and fold creases that none of these reproduce. Scoring 100% here means the
pipeline is not broken; it does not mean OCR works on a real bill.

## Real bills

Photographed bills are gitignored (they carry consumer name, number and address).
Drop them in this directory and add a row below with values read off the paper.

Only billing figures are recorded here. Consumer name, consumer number, RR
number and address are deliberately never written down, in this file or
anywhere else — the same rule the extraction prompt and schema enforce.

| file | units_consumed | total_amount | billing_days | tariff_slab | period_end | notes |
|---|---|---|---|---|---|---|
| `bill1.png` | — | 1768.00 | — | — | 05/04/2026 | **payment receipt, not a consumption bill** — no units, days or slab printed. Correct extraction returns null for those; a number is a hallucination. |
| `real_bill_01.jpg` | 239 | 418.00 | — | — | — | **payment receipt**, photographed handheld at 90°. Units ARE printed, as `Units: 239` overprinted on the pre-printed SAC-code line — verified at 3× zoom. Total confirmed in words: "Four Hundred And Eighteen Only". No billing period, no slab, no meter readings, so `billing_days` is correctly null and the bill is correctly rejected. Implied rate ₹1.75/kWh — this is the bill that exposed the ₹2.00 rate floor. |

### What these two real bills prove, and what they don't

Both are **payment receipts**, not consumption bills. Between them they have
proven a lot: extraction reads overprinted dot-matrix text, recovers a sideways
photo via auto-rotation, returns null rather than inventing absent fields, and
the validation gate correctly refuses input the engine cannot use.

They have **not** proven the full pipeline. Neither prints `billing_days` or a
tariff slab, so neither can reach the engine, and no ranked breakdown has ever
been computed from real extracted numbers. That still needs a standard LT-1A
computer-printed consumption bill or a TNPDCL portal PDF.

## Privacy

The synthetic bills carry deliberately fake consumer name, number and address so
the privacy rule is testable: extraction must never return them. `validate_real.py`
scans every response for these strings and fails the run if any appears.

Fake identifiers used: `TEST CONSUMER`, `00000000000`, `1 TEST STREET, CHENNAI 600001`.

These are placeholders and are never copied from a real bill — these fixtures are
committed, and the rule that forbids extracting consumer identity equally forbids
us shipping someone's in a test asset.
